# Egypt Itinerary Planner v3 设计

日期：2026-07-30

## 背景

原 Dashboard 主要解决“把已查到的价格录入后评分”的问题，但当前用户的日程已经收敛：

- 不再规划中国国内段。
- 固定国际进出：
  - 2026-09-30 02:00 从北京起飞。
  - 2026-09-30 09:00 到达开罗。
  - 2026-10-07 14:45 从开罗起飞返程。
- 核心任务变成：规划埃及段每天怎么走、住哪里、哪些转场要订、两套路线如何取舍。

因此 v3 不再以航班比价表为中心，而是做一个“埃及段行程规划器”。

## 目标

v3 要回答四个问题：

1. 9/30 到 10/7 每天具体怎么安排。
2. A1 和 A2 两种埃及路线哪个更适合。
3. 哪些转场、酒店、项目需要马上查询或预订。
4. 如果某个关键转场不可行，应该怎样自动改行程。

## 非目标

- 不再处理北京、兰州、长春等中国国内段。
- 不做全平台机票低价爬虫。
- 不保存账号密码、cookie、token。
- 不自动下单。
- 不把未查到的交通、酒店、项目包装成确定结论。

## 固定约束

### 航班约束

- 9/30 上午 09:00 到达开罗。
- 10/7 下午 14:45 从开罗起飞。
- 10/7 当天如果从赫尔格达飞回开罗，必须预留国际航班缓冲。
- 如果开罗到达时间晚于 11:00，标红为高风险。
- 如果无法确认 10/7 早班赫尔格达到开罗，自动推荐 10/6 回开罗。

### 旅行偏好

- 历史景点和红海都要覆盖。
- 方案 A 是主方向：开罗 + 卢克索 + 赫尔格达。
- 允许加入阿斯旺，但如果去阿斯旺，核心目的必须是阿布辛贝。
- 阿斯旺方案要明确说明代价：节奏更赶、红海时间更短、转场风险更高。

## 两套候选方案

### A1：开罗 + 卢克索 + 赫尔格达，均衡推荐版

定位：历史和红海兼顾，节奏最稳。

```text
9/30  开罗抵达，入住/休整，GEM 或市区轻量活动
10/1  金字塔 + 狮身人面像 + 开罗市区
10/2  开罗 → 卢克索，卡尔纳克神庙 + 卢克索神庙
10/3  卢克索西岸：帝王谷 + 哈特谢普苏特神庙 + 门农巨像
10/4  卢克索 → 赫尔格达，包车转场，下午入住红海酒店
10/5  赫尔格达红海一日游或浮潜
10/6  赫尔格达 → 开罗，返程缓冲
10/7  开罗轻量活动或直接去机场，14:45 起飞
```

优点：

- 金字塔、GEM、卢克索核心古迹、红海都覆盖。
- 10/6 回开罗，10/7 国际航班风险低。
- 红海至少有一个完整活动日。

缺点：

- 不含阿布辛贝。
- 卢克索到赫尔格达需要包车或较长陆路转场。

### A2：开罗 + 阿布辛贝 + 卢克索 + 赫尔格达，历史强化版

定位：为阿布辛贝牺牲舒适度和红海时间。

```text
9/30  开罗抵达，入住/休整，GEM 或市区轻量活动
10/1  金字塔 + 狮身人面像，晚飞或夜车去阿斯旺
10/2  阿布辛贝强约束日，早出发，下午回阿斯旺
10/3  阿斯旺 → 卢克索，卡尔纳克神庙 + 卢克索神庙
10/4  卢克索西岸：帝王谷 + 哈特谢普苏特神庙 + 门农巨像
10/5  卢克索 → 赫尔格达，包车转场，下午入住红海酒店
10/6  赫尔格达红海半日或一日游，住赫尔格达或晚回开罗
10/7  一早赫尔格达 → 开罗，衔接 14:45 国际航班
```

优点：

- 在有限时间内覆盖阿布辛贝。
- 历史体验最强。
- 仍保留红海体验，但更短。

缺点：

- 转场密度高。
- 阿布辛贝日程很重。
- 10/7 早飞开罗是关键风险点。
- 如果 10/7 赫尔格达到开罗早班不可行，应自动改成 10/6 回开罗。

## 路线顺序原则

如果加入阿布辛贝，默认采用：

```text
开罗 → 阿斯旺/阿布辛贝 → 卢克索 → 赫尔格达 → 开罗
```

原因：

- 阿布辛贝只能从阿斯旺作为核心跳板。
- 阿斯旺在卢克索以南，赫尔格达在卢克索以东。
- 先阿斯旺再卢克索，可以从最南端逐步往北/往东移动。
- 如果先卢克索再阿斯旺，会在阿布辛贝后为了去赫尔格达再折回卢克索方向，浪费时间。

反向路线只在以下情况作为备选：

- 卢克索入境航班或价格明显优于阿斯旺。
- 用户选择尼罗河邮轮，需要按邮轮方向排布。
- 阿斯旺到赫尔格达出现可接受的直达或高效交通。

## 页面设计

### 顶部结论区

显示：

- 当前推荐方案：默认 A1。
- A2 是否值得选。
- 主要理由：
  - A1 稳定、有完整红海日。
  - A2 多阿布辛贝，但牺牲红海和缓冲。
- 当前最大风险：
  - A2 的 10/7 早班赫尔格达 → 开罗。

### 两方案对比区

左右或标签页切换：

- A1 均衡版。
- A2 阿布辛贝版。

每个方案显示：

- 城市顺序。
- 酒店晚数。
- 红海有效时间。
- 转场次数。
- 必订交通。
- 风险等级。

### 每日行程轴

每一天拆为：

- 上午
- 下午
- 晚上

每个时间块显示：

- 城市。
- 景点或转场。
- 建议方式。
- 预计耗时。
- 是否必须预订。
- 风险提示。

### 待查询任务区

A1 待查询：

- 开罗 → 卢克索交通。
- 卢克索 → 赫尔格达包车。
- 赫尔格达 → 开罗交通。
- 开罗酒店。
- 卢克索酒店。
- 赫尔格达酒店。
- 红海一日游或半日游。

A2 额外待查询：

- 开罗 → 阿斯旺交通。
- 阿布辛贝一日游或航班。
- 阿斯旺 → 卢克索交通。
- 10/7 早班赫尔格达 → 开罗是否足够早。

### 风险和自动重排区

规则：

- 10/7 开罗到达时间晚于 11:00：高风险。
- 10/7 赫尔格达 → 开罗无早班：A2 自动改成 10/6 回开罗。
- 阿布辛贝当日如果返回太晚：10/3 卢克索活动自动减少。
- 红海不足半天：标记为“红海体验不足”。
- 任一交通未查到：该方案不可最终推荐，只能作为待确认方案。

### query_tasks

`query_tasks` 表示“助手待查询任务”，不是用户待办。每个任务都应由 Codex/助手主动执行查询、整理候选、回填结果并触发行程重算。用户只负责登录、验证码、短信验证、最终购买确认等必须本人处理的动作。

```json
{
  "id": "a2-hrg-cai-1007-early",
  "option_ids": ["A2_ABU_SIMBEL_HRG"],
  "category": "transport",
  "title_zh": "10/7 赫尔格达 → 开罗早班",

  "success_criteria_zh": "到达开罗不晚于 11:00",
  "status": "assistant_pending",
  "owner": "assistant"
}
```

## 查询与浏览器策略

- 优先使用 Chrome 当前登录态。
- Codex 内置浏览器作为兜底。
- 不保存账号密码、cookie、token。
- 所有待查询任务默认由助手执行，不要求用户自己查。
- 需要验证码、短信、滑块时暂停，由用户完成验证；验证后助手继续查询。
- 航班/交通由助手优先自动查并回填候选。
- 酒店和项目也由助手查询；如果平台阻断自动读取，助手应改用可访问来源交叉查询，或请用户完成登录/验证码后继续，不把查询责任转交给用户。
- 查询结果必须记录来源平台、链接、查询时间、价格、关键条件和置信度。
- 查询失败不是用户待办，而是系统状态：`blocked_by_login`、`blocked_by_captcha`、`no_result_found`、`needs_retry` 或 `assistant_pending`。

## 查询任务状态

```text
assistant_pending   助手尚未开始查
searching           助手正在查
blocked_by_login    平台要求登录，等待用户完成登录
blocked_by_captcha  平台要求验证码/滑块，等待用户完成验证
no_result_found     助手已查，未找到满足条件的结果
found_candidates    助手已查到候选，等待系统重算
selected            候选已被纳入推荐方案
needs_retry         来源失败或信息不足，需要助手换来源重试
```

页面文案必须避免“请用户自行查询”。正确表达是：

```text
待助手查询
正在查询
需要你完成登录后继续
已查到候选
未找到可用结果
```

## 评分逻辑

v3 不再只看价格和飞行时间，而是做行程适配评分。

```text
total_score =
  stability_score * 0.35 +
  experience_score * 0.35 +
  transfer_score * 0.20 +
  cost_score * 0.10
```

解释：

- stability_score：是否有返程缓冲、关键交通是否可订。
- experience_score：金字塔/GEM/卢克索/红海/阿布辛贝覆盖度。
- transfer_score：转场次数、是否过早/过晚、是否折返。
- cost_score：交通、酒店、项目预算。

默认 A1 得分应通常高于 A2，除非用户把阿布辛贝权重调高。

## 推荐文案规则

系统必须直接说清楚取舍：

```text
推荐 A1，因为它保留完整红海日，并在 10/6 回开罗，10/7 国际返程风险低。
不推荐默认 A2，是因为阿布辛贝会压缩红海，并且依赖 10/7 赫尔格达早班飞开罗。
如果你认为阿布辛贝优先级高于红海舒适度，可以选择 A2，但需要优先确认 10/7 早班航班。
```

## 测试要求

- A1 时间轴必须包含开罗、卢克索、赫尔格达。
- A2 时间轴必须包含阿布辛贝。
- A2 必须标记 10/7 赫尔格达 → 开罗早班为高优先级查询任务。
- 如果 10/7 开罗到达时间晚于 11:00，A2 风险必须变高。
- 如果 A2 改为 10/6 回开罗，红海时间必须减少并显示代价。
- 路线顺序说明必须解释“先阿斯旺再卢克索”的原因。
- 页面不应出现中国国内段。
